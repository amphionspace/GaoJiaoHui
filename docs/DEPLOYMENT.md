# 发布、监控与回滚

## 发布前

1. 备份现有工作区、线上目录及实际运行配置，不直接覆盖线上文件。
2. 在新版本目录安装固定 Python 依赖及前端锁文件依赖，通过测试和生产构建。
3. 私密配置通过服务器提供，不进入 Git、构建产物与日志；已在聊天出现过的凭据应由账号负责人轮换。
4. 保留当前 ASR 新旧网关分流，平台迁移完成后再统一。固定 IP 仍需保留域名 TLS/SNI 校验。

## 单机生产

建议目录 `/opt/amphion-gjh/releases/<version>`，`/opt/amphion-gjh/current` 指向通过验收的版本，每版包含 `.venv`、`frontend/dist` 和 `server`。私密环境文件放 `/etc/amphion-gjh/runtime.env`，权限 600，由系统服务读取。

`deploy/amphion-gjh.service` 是待审阅模板，使用专用 `amphion` 用户、只读文件系统与故障重启。启动前创建 `.journey-state` 并使运行账号拥有该目录，私密 JSON 配置也须允许该账号读取。**现有服务器有自己的服务及路径，先对照再调整，不能直接覆盖现有 unit。** 2026-10-21 已部署的实际路径与回滚方式见 [demo1 发布记录](DEMO1.md)。

HTTPS 入口反代到 `127.0.0.1:8766`；反代超时至少 300 秒。设置连接/请求频率与上传大小限制，不记录带 `api_key` 查询参数的 WS URL，不开放内部模型端口。

```sh
curl --fail http://127.0.0.1:8766/api/health
curl --fail http://127.0.0.1:8766/api/config
systemctl status amphion-gjh.service
```

应用健康接口需 `frontend_built=true`；再通过工作人员设置检查文本与声音。健康 HTTP 200 不算业务验收。至少运行本人录音、摘要/回信、本人音色自动播放和打印预览；停止或切页后不得继续录音或响起旧音频。

## 监控与容量

- 分别监控应用存活、ASR、文本生成和 TTS 注册/合成的成功率与延迟。日志只记录状态和请求编号，不记录原始录音、讲述或密钥。
- 限流与鉴权缓存目前在进程内，保持单应用进程；扩容前先引入共享限流与状态存储。
- 文本生成包括生成及事实审校，正常两次模型调用，异常最多再试一轮。单次超时 20 秒，前端最多等待 90 秒；厂商账号应设置消费上限。前端走 `/api/journey/compose/stream`：第一遍模型结果先作为草稿上屏，审校完成后替换为最终文字；打印按钮在审校结束前保持禁用。若代理层缓冲响应，草稿会退化为随最终结果一起到达，功能不受影响。
- 文本模型必须用**非推理**模型（当前 `deepseek-chat`）。推理模型的 reasoning 与正文共用 `max_tokens`，长讲述会把预算耗尽并返回空正文，表现为“整理一直失败”。上游 429/5xx 会自动重试一次（0.6 秒）；若换回推理模型，需把 `MAX_COMPLETION_TOKENS` 提到 8192 以上并接受 30–60 秒时延。
- 管理模式下 ASR 临时凭证在服务端缓存 40 秒（凭证本身 60 秒），前端在开场故事播放时预取；同一个凭证可服务访问校验与 WS 握手，避免每次录音都重新签发。
- 音频队列上限 10 条，参考音频限制大小和时长；克隆对话音频缓存上限约 20 MB，离开页面停止操作，重新开始或卸载释放缓存。
- ASR 识别合成内容正确不等于音色相似，须本人试听验收。

## 回滚

保留上一版本目录与配置快照。新版本失败时将 `current` 指回上一版，再重启应用；不还原其他人的网关配置。确认主要流程恢复后排查失败版本。仅 TTS 失效时保留文本及打印服务，明确提示声音不可用。

本机使用 `scripts/run_local.py` 统一启动两个服务。电脑或终端停止后服务不会继续运行；长期现场部署应使用系统服务，不能以“浏览器保持打开”代替进程托管。
